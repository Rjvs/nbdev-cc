# nbdev Project Development Skill

You are working on an nbdev project - a literate programming environment where Python libraries are developed in Jupyter notebooks. Code, tests, and documentation coexist in the same notebooks.

> **Tool selection**: see the project's CLAUDE.md for jupyter-mcp vs nbdev MCP tool guidance.

## Philosophy: Progressive Discovery

The heart of nbdev is **progressive discovery** - the notebook documents your journey of understanding, which then guides newcomers along the same path.

### Notebooks Tell a Story

A notebook is not just organized code - it's a narrative. The order of cells matters because readers follow your discovery process:

1. **Start with the simplest case** - introduce concepts one at a time
2. **Build complexity gradually** - each cell adds one new idea
3. **Explain the "why"** - markdown cells provide context, motivation, reasoning
4. **Show before you tell** - demonstrate with examples before formal definitions
5. **Tests are examples** - they show expected usage and behavior, not just verify correctness

### The Development Process IS the Documentation

As you figure out a problem, you're simultaneously teaching future readers (including yourself in 6 months). This means:

- **Write prose between code cells** explaining what you're about to do and why
- **Keep the messy exploration** (cleaned up) - it shows the reasoning
- **Order cells pedagogically** - not by what's "logical" for the module, but what's easiest to understand
- **Use `@patch`** to introduce class methods one at a time, with explanation between each

The pattern is: show simple case → explain → demonstrate edge case → iterate. This creates documentation that teaches rather than just describes.

## Core Concepts

**Literate Programming**: In nbdev, notebooks ARE the source of truth. Python modules are generated FROM notebooks via export. Never edit generated `.py` files directly - always edit the source notebooks.

**Directives**: Special comments starting with `#|` control export behavior, documentation, and testing. See `references/directives.md` for the complete list.

**Notebook Structure**: `.ipynb` files are JSON documents. When editing programmatically, you must understand the cell structure. See `references/notebook-format.md` for details.

## Project Structure

A typical nbdev project:

```
project-root/
├── settings.ini          # All nbdev configuration
├── nbs/                   # Source notebooks (configurable via nbs_path)
│   ├── _quarto.yml        # Quarto configuration for docs
│   ├── index.ipynb        # Becomes README.md and docs homepage
│   ├── 00_core.ipynb      # Number prefix defines generation order (see below)
│   ├── 01_utils.ipynb     # Can import from 00_core but not vice versa
│   └── ...
├── project_name/          # Generated Python package (lib_path)
│   ├── __init__.py
│   ├── core.py            # Generated from 00_core.ipynb
│   └── utils.py           # Generated from 01_utils.ipynb
├── _docs/                 # Generated documentation (doc_path)
└── .github/workflows/     # CI/CD for testing and docs
```

## Module Generation Order

The numeric prefix on notebook filenames (e.g., `00_`, `01_`, `02_`) defines the order in which `nbdev_export` generates Python modules. **This order creates a hard dependency constraint**: a notebook can only import from modules generated by earlier (lower-numbered) notebooks. Modules from later notebooks don't exist yet at the point they would be needed.

### The Constraint

```
00_core.ipynb      → project/core.py       (generated first)
01_utils.ipynb     → project/utils.py      (can import from core)
02_features.ipynb  → project/features.py   (can import from core, utils)
03_app.ipynb       → project/app.py        (can import from core, utils, features)
```

- `01_utils.ipynb` **can** do `from project.core import Foo` (core is generated before utils)
- `00_core.ipynb` **cannot** do `from project.utils import Bar` (utils doesn't exist when core is generated)

This applies to `nbdev_export`, `nbdev_test`, and `nbdev_docs` - all of which process notebooks in filename order.

### Planning Around the Constraint

1. **Put foundational code in low-numbered notebooks** - types, base classes, constants, and shared utilities belong early
2. **Higher-numbered notebooks build on lower ones** - features depend on core, app depends on features
3. **If two modules need each other, put them in the same notebook** - circular dependencies mean the code belongs together in one notebook (or refactor so the shared part moves to an earlier one)
4. **Leave gaps in numbering** (00, 05, 10...) so you can insert new modules later without renaming everything

### Cross-Module Export Workaround

You can use `#| export other_module` on individual cells to export to a module other than the notebook's `default_exp` target. This provides a workaround when a helper logically belongs in a later module's namespace but must be defined early for dependency reasons:

```python
# In 01_utils.ipynb (default_exp utils)
#| export data
def parse_record(raw):
    """Parse a raw data record. Lives in data module but defined early."""
    ...
```

This exports `parse_record` to `project/data.py` even though it's defined in `01_utils.ipynb`. Later, `03_data.ipynb` can re-export or extend it. Use sparingly — it can make code harder to find.

### Common Pitfall

You define a helper in `05_helpers.ipynb` and later realize `02_data.ipynb` needs it. You **cannot** simply import it - `02_data` is generated before `05_helpers`. The fix is to move the helper into `02_data.ipynb` (or an even earlier notebook like `01_utils.ipynb`) so it's available to all downstream modules.

### Editable Install

Cross-notebook imports require `uv pip install -e .` (run once after clone, and again after changing `settings.ini` or `pyproject.toml`). Without it, `ModuleNotFoundError` occurs even though the generated `.py` files exist.

## Notebook Cell Patterns

### Module Definition Cell (first cell of notebook)

```python
#| default_exp core
```

This names the module where exports go. The above creates `project_name/core.py`.

### Export Cell

```python
#| export
def my_function(x):
    """Docstring here."""
    return x * 2
```

Exported functions/classes go into the module AND documentation.

### Internal Export (not in `__all__`)

```python
#| exporti
def _internal_helper():
    pass
```

### Test Cell (any non-exported cell)

```python
# This is a test - no directive needed
assert my_function(2) == 4
```

## The `@patch` Decorator

Use fastcore's `@patch` to split class definitions across cells - essential for literate programming:

```python
#| export
class Dog:
    def __init__(self, name): self.name = name
```

```markdown
The `Dog` class stores a name. Now let's teach it to bark:
```

```python
#| export
from fastcore.basics import patch

@patch
def bark(self: Dog):
    """Make the dog bark."""
    return f"{self.name} says woof!"
```

```python
# Test the method
dog = Dog("Rex")
assert dog.bark() == "Rex says woof!"
```

`@patch` lets you split class definitions across cells (with prose between methods), test each method immediately after defining it, and even add methods to external classes without subclassing. See `references/fastcore.md` for patterns, or the **fastcore** skill for the full API.

## Essential fastcore Utilities

nbdev projects heavily use fastcore. Key utilities:

| Utility | Import | Purpose |
|---------|--------|---------|
| `@patch` | `fastcore.basics` | Add methods to classes |
| `@delegates` | `fastcore.meta` | Replace `**kwargs` with explicit params |
| `store_attr` | `fastcore.basics` | Auto-store `__init__` arguments |
| `L` | `fastcore.foundation` | Enhanced list with functional methods |
| `test_eq` | `fastcore.test` | Test equality (better than assert) |
| `@typedispatch` | `fastcore.dispatch` | Multiple dispatch by type |

### Common Imports

```python
#| export
from fastcore.basics import patch, store_attr, GetAttr
from fastcore.meta import delegates
from fastcore.foundation import L
from fastcore.test import test_eq, test_ne, test_fail
```

See `references/fastcore.md` for nbdev-specific patterns, or the **fastcore** skill for the full API.

## Testing

### fastcore Test Functions

Use fastcore's test utilities instead of bare `assert`:

```python
from fastcore.test import test_eq, test_ne, test_fail

test_eq(add(1, 2), 3)           # Equality (shows both values on failure)
test_ne(add(1, 2), 4)           # Inequality
test_fail(lambda: 1/0)          # Exception expected
test_fail(lambda: int("abc"), contains="invalid literal")  # Exception with message check
```

### Test Flags

Configure in `settings.ini` with `tst_flags`:

```python
#| slow
# This test only runs with: nbdev_test --flags slow
def test_slow_operation():
    ...
```

### Skip Testing

```python
#| eval: false
# This cell is never executed during testing
```

## Documentation Generation

Documentation is generated via Quarto. Key directives:

| Directive | Effect |
|-----------|--------|
| `#| hide` | Hide from both module AND docs |
| `#| hide_input` | Hide code, show output in docs |
| `#| output: false` | Hide output in docs |
| `#| output: asis` | Render output as raw markdown |

### show_doc (for non-nbdev code only)

Exported cells (`#| export`) automatically generate documentation — you do **not** need `show_doc` for normal nbdev code. It exists primarily for documenting code that was *not* written in nbdev (e.g., hand-written `.py` files in a hybrid package):

```python
from nbdev.showdoc import show_doc
show_doc(some_external_function)  # Renders signature + docstring for non-nbdev code
```

If you do use it, put `show_doc` calls in their own cells (not mixed with other code).

### Excluding Content from Docs and Export

When notebook content is not ready for inclusion — drafts, debugging scaffolding, internal helpers, or work-in-progress — use the appropriate directive or technique:

| I want to... | Code cells | Markdown cells |
|---|---|---|
| Hide everything (no export, no docs) | `#\| hide` | `:::{.content-hidden}` |
| Hide from docs but still execute | `#\| include: false` | `:::{.content-hidden}` |
| Export to module but hide from public API/docs | `#\| exporti` | N/A |
| Show in docs but never execute | `#\| eval: false` | N/A |
| Hide the code but show the output | `#\| hide_input` | N/A |
| Hide a single line of code | `#\| hide_line` (inline) | N/A |
| Show code but hide the output | `#\| output: false` | N/A |
| Make code collapsible (not hidden) | `#\| code-fold: true` | N/A |

For markdown cells, Quarto's `:::{.content-hidden}` div keeps content visible and editable in the notebook while excluding it from generated docs:

```markdown
::: {.content-hidden}
# Draft notes — visible in notebook, hidden from docs
:::
```

See `references/directives.md` for full syntax details on each directive, including conditional hiding by output format.

## Best Practices

- **Delete orphaned modules manually** — changing `default_exp` doesn't remove the old `.py` file
- **Prefix scratch notebooks with `_`** (e.g., `_scratch.ipynb`) — nbdev ignores files starting with underscore
- **Restart kernel and Run All** before `nbdev_prepare` to catch hidden state from out-of-order execution
- **Clean up scratch cells** before committing — promote useful experiments into proper export + test cells

### Hybrid Packages

nbdev supports **hybrid packages** where some modules are exported from notebooks and others are hand-written `.py` files. This is useful when adopting nbdev incrementally, when some modules suit traditional development (CLI entry points, generated code), or when collaborators contribute `.py` files directly. Use `show_doc` to document hand-written `.py` code.
